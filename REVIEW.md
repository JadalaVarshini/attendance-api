# REVIEW.md

Review of the starter `app/main.py`. Line references are to the original starter file. All of the items below are fixed in the submitted `app/main.py`.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes`, `minutes > 10` | Grace is "strictly more than 10:00", but minutes are floored *before* the comparison, so 09:40:01 gives 10 and is treated as on time. | Shift 09:30, punch-in 09:40:01: expected 10, got 0. | Compare whole seconds (`> 600`), then floor to minutes since shift start. |
| 2 | `compute_late_minutes`, `punch_in.replace(hour=h, ...)` | The shift start is applied in the punch-in's own zone (UTC from Mongo, server-local from `fromtimestamp`), not IST. It also uses the punch-in's own calendar day, so overnight shifts (punch-in 00:05 for a 22:00 shift) come out hugely negative and show as 0 late. No truncation to whole seconds. | Any punch-in: 09:40 IST is 04:10 UTC, so it is compared with 09:30 UTC. | `shift_bounds()` builds the shift start/end as IST instants for the *attendance date* (end falls on the next day for overnight shifts). Punch times are truncated to seconds on input. |
| 3 | `compute_work_hours`, `round(x, 2)` | Python `round` is banker's rounding on a binary float, but R4 says half-up. | 18 s is 0.005 h and must give 0.01; 1 min 30 s is 0.025 h and must give 0.03. | Exact integer arithmetic: `floor((seconds*200 + 3600) / 7200) / 100`. |
| 4 | `compute_overtime`, `max(0, ...)` | R3 needs >= 30 minutes before any overtime counts; the starter counts 1 minute. | Out at 18:45 on an 18:30 shift: expected 0, got 15. | Return the minutes only if >= 30. |
| 5 | `compute_overtime`, `replace(... tzinfo=IST)` | Subtracts an aware datetime from the naive `punch_out` that PyMongo returns, so it raises `TypeError` (HTTP 500). Shift end is always on the record's date, so overnight shifts (end next day) give wildly wrong overtime. | Punch out on any record read back from Mongo. | The client is `tz_aware=True`, and the shift end comes from `shift_bounds()` (+1 day for overnight). |
| 6 | `create_employee`, find-then-insert | Race: parallel creates of one `emp_code` can all pass the check, giving several 201s and duplicates. | 20 concurrent POSTs of the same code. | Unique index on `emp_code`, catch `DuplicateKeyError` and return 409. |
| 7 | `EmployeeIn` (and `PunchInIn`) | No validation at all: `emp_code` format, email, lengths, `HH:MM`, a real `joined_on` date, `shift_start != shift_end`. `punched_at: Optional[int]` accepts `1.0` and `"123"` via pydantic coercion, and seconds-looking values. | `emp_code: "x"`, `joined_on: "2026-02-30"`, `punched_at: 1783312500` all returned 201. | Patterns and length limits from the contract, a date validator, a model validator, and a strict `int` with the epoch-ms range for every instant. |
| 8 | `create_employee`, `datetime.now()` | Naive server-local time stored as if UTC, and returned as a datetime/ISO string, not epoch milliseconds. | `created_at` in the response is a string and is off by the server's UTC offset. | `datetime.now(UTC)` stored, `dt_to_ms()` returned. |
| 9 | `list_employees`, `skip = page * page_size` | Off by one page: page 1 skips the first `page_size` employees. | `GET /employees` returns the 21st employee first. | `(page - 1) * page_size`. |
| 10 | `list_employees`, `count_documents({})` | `total` ignores the department filter. | `?department=Ops` with 3 matches reports `total` for the whole collection. | `count_documents(q)` with the same filter. |
| 11 | `list_employees`, no sort / no limits | No `ORDER BY emp_code`, so pages are unstable. `page=0`, `page_size=100000`, negatives are accepted. `if department:` ignores an empty string. | `page=0` gives a negative skip; `page_size=1000000` dumps the collection. | Sort by `emp_code`; `Query(ge=1)` and `page_size` 1..100 (422 otherwise); `department is not None`. |
| 12 | `punch_in`, `emp` not checked | An unknown employee makes `emp["shift_start"]` raise `TypeError` (500) instead of 404. | POST with `emp_code: "EMP9999"`. | `get_employee_or_404`. |
| 13 | `punch_in`, `fromtimestamp(ms/1000)` and `.date()` | Converts to the server's local zone, not UTC/IST, so `date` is wrong near midnight and depends on where the server runs. The overnight rule (R1) is missing. `ms/1000` goes through a float, and `if body.punched_at` treats a value of 0 as "now". Microseconds are not truncated. | Punch-in at 23:45 IST on a server running in UTC gets the wrong date; 00:05 for a 22:00 shift gets the next day's date. | Epoch ms to UTC datetime with integer arithmetic and truncation; `attendance_date()` implements R1 in IST including overnight shifts. |
| 14 | `punch_in`, check-then-insert | Race: two simultaneous punch-ins both pass the `find_one` and insert two records for one day. | Two parallel POSTs: two 201s, duplicate records. | Unique index on `(emp_code, date)`, catch `DuplicateKeyError` and return 409. |
| 15 | `punch_in`, `status: str` | Any string is accepted, including `ABSENT`, `LEAVE` or `"banana"`, which the punch-in endpoint must not create. | `status: "ABSENT"` returns 201. | `Literal["PRESENT","WFH","ON_DUTY"]`. |
| 16 | `punch_in` response | Adds `id` (the `_id`, which must never be exposed) and returns `punch_in` as a datetime object, not epoch ms. | Response contains `"id": "65f..."`. | `to_record()` builds the response from the contract's fields only. |
| 17 | `list_attendance`, `find(q)` then sort in Python | Loads the entire collection into memory and sorts and paginates in Python: slow and memory-heavy at 100k. Sorts only by `date`, so ties are unordered. | `GET /attendance` on 100k documents is slow; page contents shift between calls. | `find().sort([("date",-1),("emp_code",1)]).skip().limit()`, backed by indexes. `total` from `count_documents(q)`. |
| 18 | `list_attendance`, no validation | `page=0` gives a negative slice. `page_size` is uncapped. `date_from > date_to` is not rejected. Dates and `status` are not validated. | `page=0`, `date_from=garbage`, `status=NOPE` all return 200. | `Query` constraints, strict date parsing, a `Literal` status enum, and 422 for `date_from > date_to`. |
| 19 | `list_attendance`, output | Leaks `id`, returns raw datetimes, and omits defaults for legacy documents (no `history`, no `half_day`). | Legacy record returns no `history` key. | Same `to_record()`: epoch ms, `history: []`, `half_day: false`, `late/overtime: 0` when missing. |
| 20 | `/health` | Always returns `ok`, even if MongoDB is down. | Stop Mongo; `/health` still says 200. | Pings MongoDB and returns 503 on failure. |
| 21 | module setup | `MongoClient` is not `tz_aware` (naive datetimes everywhere) and no indexes are created, so every query is a collection scan and there is no uniqueness guarantee. | Aggregations and lists collscan; duplicates are possible. | `tz_aware=True`; idempotent index creation at startup (see DECISIONS.md). |

**Looked at and judged not a defect**

- `load_dotenv()` with its default `override=False`: variables already in the environment win over `.env`, which is what the contract requires.
- Plain `def` (not `async def`) endpoints with the synchronous PyMongo client: FastAPI runs them in a thread pool, so they don't block the event loop. I kept this design. `MongoClient` is thread-safe.
- `doc.pop("_id")` after `insert_one` in `create_employee`: it does remove the `_id`. (The defect there is the naive `created_at`, #8.)
- `IST = timezone(timedelta(hours=5, minutes=30))`: correct. IST has no DST, so a fixed offset is right.
- `int((a - b).total_seconds() / 60)` as a floor: fine for positive values (negatives are clamped to 0 anyway), but I replaced it with `// 60` on integer seconds to avoid float division.
